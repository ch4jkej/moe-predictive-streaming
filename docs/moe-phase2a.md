# Phase 2A: exact MoE router selections and expert-cache trace

The original router stays unchanged. The trace is opt-in and is generated by the existing GPU expert-cache callback. It records the expert IDs already read by llama.cpp; no extra GPU readback is performed.

## Quick test on Windows

Unpack the *new* GitHub Actions build into one folder. Keep all DLLs with the executables. In PowerShell, change only the local model path below, and run from the unpacked binary directory.

~~~powershell
$model = "D:\Models\Ling-3.0-tiny-Q8_0.gguf"
$env:MOE_TRACE_PATH = (Join-Path (Get-Location) "ling-phase2a.jsonl")
.\llama-cli.exe -m $model -ngl 99 -cmoe --moe-cache-mib 2048 -c 2048 -b 128 -ub 8 -n 128 -t 6 --temp 0 --seed 42 -p "Explain how a sparse MoE chooses experts."
Remove-Item Env:\MOE_TRACE_PATH
~~~

The trace requires BOTH -cmoe and a nonzero --moe-cache-mib. Full-GPU inference, zero-cache CPU-MoE, and cache bypass (e.g. very large prefill batches) are not traced. Small -ub 8 microbatches make the cache path more likely but can change prefill speed.

The trace file is in JSON Lines format and is **appended** on each run. Use a fresh filename for each experiment. It may include information about processed text through its routing patterns; do not publish it by default.

## JSONL schema

Each line is an object containing:

- event: moe_selection
- layer: original 0-based MoE layer index
- call: per-layer call index (starts from zero for each model context; not an absolute token index)
- tokens: count of tokens in this layer invocation
- k: number of experts selected per token
- expert_ids: token-major, flattened top-k IDs, exactly as the original router selected them. Reconstruct with ids[token_index*k + expert_rank].
- cache_hits: DISTINCT expert IDs already resident in this GPU cache bank
- cache_misses: DISTINCT expert IDs uploaded to the GPU cache
- missing_expert_ids: IDs of experts selected but not cached
- upload_bytes: bytes of selected expert weights submitted to GPU transfer API, NOT bytes read from NVMe
- readback_sync_us: CPU-wall time to read the IDs and synchronize the GPU backend (operation already present in the cache)
- cache_plan_us: CPU LRU planning time
- enqueue_us: CPU time issuing asynchronous transfer commands; NOT completion or stall time

The tracer does not capture hidden vectors, router logits/probabilities, NVMe I/O timings, GPU DMA completion or exact global token positions. Do not infer them from enqueue_us.

## Check output

~~~powershell
$events = @(Get-Content .\ling-phase2a.jsonl | ForEach-Object { $_ | ConvertFrom-Json })
$events.Count
$events | Select-Object -First 4 layer, call, tokens, k, cache_hits, cache_misses
$hits = ($events | Measure-Object cache_hits -Sum).Sum
$misses = ($events | Measure-Object cache_misses -Sum).Sum
$bytes = ($events | Measure-Object upload_bytes -Sum).Sum
"GPU cache hit ratio: {0:N2}%" -f (100*$hits/[Math]::Max(1, ($hits+$misses)))
"Expert weights submitted: {0:N3} GiB" -f ($bytes/1GB)
~~~

Check that layers and calls appear, and preserve stderr logs with the final llama_moe_cache summary. Compare inference quality and decode speed against identical settings without the environment variable. Recording and flushing the trace has overhead; do not judge predictive speedups from a traced run.

The required performance comparison is the baseline without trace versus the same CPU-MoE cache budget with trace. If GPU cache conditions change, do not compare as though only tracing changed.
